# 문서 운영 정책

## 목적

문서의 양보다 정확성, 소유권, 추적성, 검증 가능성을 유지하는 것이 목적입니다.

## 기준 정보 원칙

- 현재 시스템 구조는 `architecture/`가 기준입니다.
- 결정 이유와 당시의 대안은 `decisions/`가 기준입니다.
- 완료된 작업 문서는 현재 동작의 기준으로 사용하지 않습니다.

## 문서 작성 스타일

- **기본 문체:** 개조식과 명사형 종결 사용
- **항목 구성:** 항목 하나당 핵심 내용 하나만 기술
- **의미 보존:** 조건·주체·예외 생략 금지, 필수·권장·허용·금지 구분
- **서술문 허용:** 배경·결정 이유·인과관계 설명에 짧은 서술문 사용
- **형식 선택:** 절차는 번호 목록과 구체적인 행동·기대 결과, 비교는 표, 단순 나열은 글머리표 사용
- **정보 배치:** 목적·적용 범위·핵심 내용을 앞부분에 배치
- **중복 최소화:** 상세 규칙은 기준 문서에서 관리하고 다른 문서에서는 요약과 링크 제공
- **템플릿 안내:** 작성 지침과 실제 본문 구분, 프로젝트 적용 시 불필요한 안내 제거

### 적용 범위

- 새 문서와 기존 문서의 수정 부분부터 적용
- 기존 문서 전체의 일괄 전환은 필수 아님, 가독성 개선이 필요한 파일부터 순차 정리
- 문체 변경 시 기존 규칙의 의미와 의무 수준 유지
- 승인된 ADR은 원문 보존 원칙에 따라 문체 전환 대상에서 제외

### 작성 예시

기존 표현:

> 모든 핵심 문서는 담당 팀과 마지막 검토일을 표시합니다. 코드 변경으로 내용이 달라졌다면 정기 검토일까지 기다리지 않고 같은 변경 요청에서 갱신합니다.

개선 표현:

- **표시 필수:** 핵심 문서의 담당 팀·마지막 검토일
- **갱신 시점:** 코드 변경으로 문서 내용이 달라지는 경우, 정기 검토일까지 기다리지 않고 동일 변경 요청에서 갱신 필수

## 소유권과 검토

모든 핵심 문서는 담당 팀과 마지막 검토일을 표시합니다. 코드 변경으로 내용이 달라졌다면 정기 검토일까지 기다리지 않고 같은 변경 요청에서 갱신합니다.

## 수명 주기

- 아키텍처, 가이드: 현재 상태에 맞게 직접 갱신
- ADR: 승인 후 원문을 보존하고 새 ADR로 대체
- 작업 문서: `active/`에서 작성하고 완료 후 `completed/`로 이동

## 변경 유형별 흐름

아래 흐름은 필요한 문서만 선택하기 위한 기준이며, 모든 작업에 ADR을 강제하지 않습니다.

### 일반 기능

방향과 구조가 이미 정해진 일반 기능은 다음 흐름으로 충분합니다.

```text
Requirement
    ↓
Task
    ↓
Code
    ↓
Test
```

### 아키텍처 결정이 필요한 기능

되돌리기 어려운 선택을 기록해야 하는 경우 ADR을 먼저 작성합니다.

```text
Requirement
    ↓
ADR
    ↓
Architecture
    ↓
Task
    ↓
Code
    ↓
Test
```

## 문서 작성 판단 기준

| 문서 | 작성해야 하는 경우 | 생략할 수 있는 경우 |
| --- | --- | --- |
| Requirement | 새로운 사용자 결과, 성공 조건 또는 품질 요구를 정의할 때 | 기존 요구사항을 그대로 충족하는 작은 수정 |
| ADR | 장기간 영향을 주거나 되돌리기 어렵고 이유를 보존해야 하는 결정 | 일상적인 구현 선택이나 쉽게 바꿀 수 있는 세부 사항 |
| Architecture | 시스템 경계, 구성 요소, 흐름, 배포, 데이터 또는 공통 원칙이 바뀔 때 | 현재 구조 설명이 달라지지 않는 내부 수정 |
| Task | 여러 파일·모듈을 횡단하거나 진행 상태와 인수인계가 필요할 때 | 한두 파일의 명백하고 짧은 수정 |

Task를 생략해도 테스트와 문서 영향 확인은 생략하지 않습니다. 기존 문서가 있으면 같은 목적의 새 문서를 만들지 않고 기존 문서를 갱신합니다.

## 문서 간 추적 관계

- Requirement는 관련 ADR, Task와 테스트를 링크합니다.
- ADR은 영향을 받은 Architecture를 링크합니다.
- Task는 구현 근거가 되는 문서와 검증 결과를 링크합니다.
- 완료된 Task는 현재 상태의 기준이 아니므로 결과를 Architecture에 반영한 후 이동합니다.

## 변경 요청 확인 사항

- 기준 문서가 하나로 유지되는가?
- 요구사항, 설계, 테스트 사이의 연결이 있는가?
- 명령과 예제를 실제로 실행할 수 있는가?
- 비밀 값이나 개인정보가 포함되지 않았는가?
- 깨진 내부 링크가 없는가?
- 변경 규모에 맞는 문서만 작성했는가?
- 완료된 작업 결과가 현재 상태 문서와 CHANGELOG 또는 릴리스 안내에 반영되었는가?

## 티어 상향 기준

이 저장소는 standard 티어입니다. 다음이 반복되면 원본 템플릿 저장소(`project-sample`)의 `templates/full/`에서 해당 모듈을 가져옵니다(`scripts/add-module.sh`).

- 방향 미확정인 큰 변경에서 대안 비교 기록이 필요한 경우: `docs/rfcs/`
- 외부 팀이나 다른 서비스가 소비하는 API·이벤트·스키마가 생긴 경우: `docs/specs/`
- 배포·장애 대응을 당번이 돌아가며 수행하는 경우: `docs/operations/`
- 아키텍처 통합 문서가 관점별로 담당자가 갈릴 만큼 커진 경우: `docs/architecture/` 개별 문서와 C4
